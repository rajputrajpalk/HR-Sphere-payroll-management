🏛️ Section 1: Project Overview & Architecture (Q1 – Q6)
Q1. Can you give a high-level overview of the HR Sphere project and the business problem it solves?
Answer:
HR Sphere is a multi-tenant HR and Payroll Management SaaS web application built with Java 21, Spring Boot 3.3, Spring Security, Spring Data JPA, and Thymeleaf.
In traditional HR software, organizations often need separate installations or pay for bloated enterprise tools. HR Sphere solves this by providing a unified, multi-tenant SaaS platform where multiple companies can independently manage their workforce hierarchy (Company Admins, HR Managers, and Employees), delegate and track tasks, manage employee leave requests, and calculate monthly payroll statements with automated net pay computation, while maintaining strict data isolation.

Q2. What technology stack did you choose for this project and what was the rationale behind each choice?
Answer:

Java 21 (LTS): Leverages modern language enhancements like pattern matching, enhanced switch expressions, and robust performance.
Spring Boot 3.3: Accelerates enterprise development with auto-configuration, starter modules, HikariCP connection pooling, and embedded Tomcat server.
Spring Security 6: Implements Role-Based Access Control (RBAC), BCrypt password hashing, session lifecycle control, and custom UserDetails authentication.
Spring Data JPA & Hibernate: Provides Object-Relational Mapping (ORM), automated database schema synchronization (ddl-auto: update), and declarative repository queries.
H2 SQL Database (File Mode): Zero-configuration, disk-persistent SQL database (./data/hrspheredb.mv.db) suitable for local deployment, integration testing, and rapid demonstrations with an embedded Web Console.
Thymeleaf: Secure, server-side template engine that binds directly with Spring MVC models and prevents typical SPA state synchronization overhead.
Q3. What architectural pattern does this application follow?
Answer:
The application follows the Layered (N-Tier) MVC Architecture:

Presentation Layer (Web / View): Thymeleaf templates and Spring MVC Controllers (SuperAdminController, CompanyAdminController, HRController, EmployeeController, DashboardController).
Security & Authentication Layer: SecurityConfig, CustomUserDetailsService, and Roles.
Business & Domain Model Layer: JPA Entities (Company, AppUser, Task, LeaveApplication, Payroll) with encapsulated business methods.
Persistence / Data Access Layer: Spring Data JPA interfaces extending JpaRepository.
Database Layer: Embedded persistent H2 SQL database engine.
Q4. How is Multi-Tenancy implemented in HR Sphere?
Answer:
HR Sphere uses the Discriminator Column (Shared Database, Shared Schema) multi-tenancy model.
Every tenant-scoped entity (app_users, tasks, leave_applications, payrolls) maintains a foreign key reference (company_id) pointing to the companies table.
All repository queries filter explicitly by company_id, ensuring strict tenant isolation. This design was chosen because it is lightweight, allows instant provisioning of new companies without running dynamic DDL/schema creation scripts, and simplifies aggregate analytics for Super Admins.

Q5. What is the user role hierarchy and how do access boundaries work?
Answer:
The platform defines a 4-tier strict delegation hierarchy:

Super Admin: System owner. Provisions tenant companies, creates initial Company Admins, and can suspend entire organizations.
Company Admin: Tenant owner. Onboards HR Managers for their organization within allocated quota limits (maxHRs).
HR Manager: Onboards Employees within company quotas (maxEmployees), delegates tasks, reviews/approves leave applications, and generates payroll slips.
Employee: Self-service workspace to update assigned task progress, submit leave requests, and view/download monthly payslips.
Q6. What software design patterns did you implement in this codebase?
Answer:

Repository Pattern: Abstracted database operations using Spring Data JPA (JpaRepository).
Dependency Injection / Inversion of Control (IoC): Constructor-based injection across all controllers and services.
Front Controller Pattern: Spring MVC DispatcherServlet handling incoming HTTP requests.
Data Access Object (DAO) Pattern: Decoupling domain logic from persistence mechanisms.
Factory / Builder semantics: Creating entities cleanly with encapsulated status transitions.
Strategy Pattern (Spring Security): Pluggable PasswordEncoder (BCrypt) and UserDetailsService.
🔒 Section 2: Security & Authentication (Q7 – Q12)
Q7. How does the authentication and login flow work in HR Sphere?
Answer:

The user enters credentials at /login.
Spring Security intercepts the request and invokes CustomUserDetailsService.loadUserByUsername().
AppUserRepository fetches the AppUser record from the database.
Spring Security validates the plain password against the BCrypt hash stored in app_users.password.
It verifies account health via AppUser.isEnabled().
Upon success, the user is redirected to /app, which hits DashboardController.dashboard(), inspecting granted authorities (ROLE_SUPERADMIN, ROLE_COMPANY_ADMIN, ROLE_HR, ROLE_EMPLOYEE) and redirecting to the proper dashboard.
Q8. What is the "Cascade Access Lock" feature and how is it implemented?
Answer:
The Cascade Access Lock allows a Super Admin to instantly suspend an entire company (Company.status = SUSPENDED).
Rather than updating hundreds of individual user records in the database, this is enforced inside the entity's isEnabled() method implementation of UserDetails:

java


@Override
public boolean isEnabled() {
    if (this.status != UserStatus.ACTIVE) return false;
    if (this.company != null && this.company.getStatus() != Company.CompanyStatus.ACTIVE) {
        return false;
    }
    return true;
}
If the parent company is suspended, Spring Security automatically denies authentication for every employee and admin of that company on the spot.

Q9. How are passwords stored and secured in the database?
Answer:
Passwords are never stored in plain text. We inject a BCryptPasswordEncoder bean in SecurityConfig.
BCrypt uses a salted, adaptive one-way hashing algorithm with configurable work factors (cost factor default is 10), providing strong protection against rainbow table and brute-force attacks.

Q10. How did you configure URL route security in SecurityConfig?
Answer:
Using Spring Security’s fluent API (HttpSecurity):

Public endpoints (/login, /css/**, /js/**, /h2-console/**) are set to .permitAll().
/superadmin/** requires authority ROLE_SUPERADMIN.
/companyadmin/** requires authority ROLE_COMPANY_ADMIN.
/hr/** requires authority ROLE_HR.
/employee/** requires authority ROLE_EMPLOYEE.
Any unmapped endpoint requires .authenticated().
Q11. Why did you configure .frameOptions(frame -> frame.disable()) in Spring Security?
Answer:
By default, Spring Security enables X-Frame-Options: DENY to prevent clickjacking attacks. However, the H2 Database Web Console (/h2-console) relies on HTML frames and iframes to render its table viewer and SQL execution panels. Disabling frame options for developer environments allows the H2 console to render properly.

Q12. How are user sessions and logout handled?
Answer:
When a user logs out at /logout:

The HTTP session is invalidated (invalidateHttpSession(true)).
The authentication context is cleared (clearAuthentication(true)).
The JSESSIONID cookie is deleted from the client browser.
The user is redirected to /login?logout=true.
🗄️ Section 3: Database & JPA / Hibernate (Q13 – Q18)
Q13. Can you describe the core entities and their relationships?
Answer:

Company (1) ──── (N) AppUser: One company has many staff members.
Company (1) ──── (N) Task: One company owns many tasks.
Company (1) ──── (N) LeaveApplication: One company owns all leave applications.
Company (1) ──── (N) Payroll: One company owns all salary records.

AppUser (1) ──── (N) LeaveApplication: Mapped as employee and hr (reviewer).
AppUser (1) ──── (N) Payroll: Mapped as employee (recipient).
Q14. How does H2 file-based persistence work compared to standard in-memory H2?
Answer:

In-Memory H2 (jdbc:h2:mem:testdb): All tables and data exist purely in RAM and are completely erased when the JVM stops.
File-Based H2 (jdbc:h2:file:./data/hrspheredb): H2 writes table definitions, rows, indexes, and transaction logs directly to disk in ./data/hrspheredb.mv.db. When the application restarts, all tenants, employees, tasks, and payroll history remain intact.
We also included AUTO_SERVER=TRUE, allowing external SQL inspection tools (like the browser H2 console or DBeaver) to connect simultaneously while the Spring Boot app is running.
Q15. What does spring.jpa.hibernate.ddl-auto: update do?
Answer:
ddl-auto: update instructs Hibernate on application startup to inspect JPA entity annotations (@Entity, @Table, @Column, @ManyToOne) and compare them with the physical database catalog:

If a table is missing, it runs CREATE TABLE.
If a new column is added to an entity class, it issues ALTER TABLE ADD COLUMN.
It does not drop existing columns or delete existing data, preventing data loss during iterative development.
Q16. How do Spring Data JPA method names translate into SQL queries?
Answer:
Spring Data JPA parses method signatures using its query derivation mechanism:

findByUsername(String username) translates to:

countByCompanyIdAndStatus(Long companyId, TaskStatus status) translates to:
sql

findByCompanyIdAndAssignedToId(Long companyId, Long employeeId) translates to:
sql


SELECT * FROM tasks WHERE company_id = ? AND assigned_to_user_id = ?;

Q18. How did you choose between FetchType.EAGER and FetchType.LAZY?
Answer:

FetchType.EAGER was used on direct associations needed immediately for dashboard views (such as Task.company, Task.assignedTo, and AppUser.company) to prevent LazyInitializationException during Thymeleaf template rendering.
FetchType.LAZY was used for hierarchical manager links like AppUser.managedByHR to avoid loading recursive user trees unnecessarily.
💼 Section 4: Business Logic & Workflows (Q19 – Q25)
Q19. How does Company Quota Management work?
Answer:
Each Company entity has configurable quota fields: maxHRs (default 5) and maxEmployees (default 100).
Before creating a new HR user or Employee, controllers check the current database count:

java


long currentHRCount = userRepository.countByCompanyIdAndRole(company.getId(), AppUser.UserRole.HR);
if (currentHRCount >= company.getMaxHRs()) {
    return "redirect:/companyadmin/dashboard?error=hr_limit_reached";
}
If the limit is reached, registration is aborted and an error flash parameter is displayed to the administrator.

Q20. Explain the Task Delegation and Progression Lifecycle.
Answer:

Creation: An HR Manager selects an employee under their company, specifies title, description, priority (LOW, MEDIUM, HIGH), and an optional due date. Initial status is set to PENDING.
Employee Progression: The assigned employee logs into their workspace, views their task queue, and can transition the status to IN_PROGRESS or COMPLETED.
Ownership Validation: In EmployeeController.updateTaskStatus(), we verify that task.getAssignedTo().getId() matches the authenticated user to prevent unauthorized state tampering.
Monitoring: The HR dashboard and Company Admin dashboard display live task completion percentages calculated dynamically via countByCompanyIdAndStatus().
Q21. How does the Employee Leave Application and Approval workflow operate?
Answer:

An employee submits a leave request with startDate, endDate, and reason.
A validation check ensures endDate is not before startDate.
The request is persisted in leave_applications with status PENDING.
The HR Manager views all pending company leave applications on their dashboard and can click Approve or Reject.
When approved/rejected, the hr_id reviewer stamp is recorded alongside the updated status.

Q23. How do you prevent slug and username collisions?
Answer:

Database Level: slug on companies and username on app_users have unique = true constraints and unique indexes.
Controller Level: In SuperAdminController, CompanyAdminController, and HRController, explicit findBySlug() and findByUsername() checks are executed before saving to gracefully redirect with user-friendly error messages rather than throwing raw SQL constraint violation exceptions.
Q24. What is the role of SeedData and how does it implement CommandLineRunner?
Answer:
CommandLineRunner is a Spring Boot callback interface executed once during startup after the ApplicationContext is loaded.
In SeedData.java, it verifies whether the root Super Admin (rajputrajpalk) exists:

If present, it verifies and re-syncs the active status and password hash.
If absent, it bootstraps the initial Super Admin account.
This guarantees the platform is immediately operational out-of-the-box on clean installations.
Q25. How do you ensure multi-tenant data privacy across different companies?
Answer:

Every controller retrieves the authenticated user via userRepository.findByUsername(auth.getName()).
The user's associated Company entity is extracted (user.getCompany()).
All subsequent queries strictly pass company.getId() to repository methods (e.g. taskRepository.findByCompanyIdAndAssignedToId(companyId, empId)).
Employees from Company A can never access or query data belonging to Company B.
☕ Section 5: Spring Boot & Modern Java (Q26 – Q30)
Q26. What modern Java 21 features were utilized in this project?
Answer:

Enhanced Switch Expressions: Used in AppUser.UserRole.toRoleString() for clean, exhaustive role mapping without break statements.
Text Blocks / Formatted Strings: Used for clean multiline logging and template generation.
Local-Variable Type Inference (var): Cleaner, more concise code in complex stream operations and repository queries.
Modern Date and Time API (java.time.*): LocalDate, LocalDateTime, and ChronoUnit for date math and leave duration calculation.
Q27. Why did you use Constructor Injection instead of @Autowired on fields?
Answer:

Immutability: Dependencies can be declared private final.
Testability: Makes writing unit tests straightforward because mock dependencies can be passed directly via constructors without Spring reflection test runners.
Prevents NullPointerExceptions: Guarantees that objects cannot be created in an uninitialized state.
Complies with Spring Best Practices: Recommended standard by the official Spring framework team.
Q28. How does DashboardController dynamically route users based on role?
Answer:
It reads the Authentication object injected by Spring MVC, iterates through authentication.getAuthorities(), and matches role prefixes:

java


if (hasRole(authentication, Roles.SUPERADMIN)) return "redirect:/superadmin/dashboard";
if (hasRole(authentication, Roles.COMPANY_ADMIN)) return "redirect:/companyadmin/dashboard";
if (hasRole(authentication, Roles.HR)) return "redirect:/hr/dashboard";
return "redirect:/employee/dashboard";
This creates a single entry point (/dashboard or /app) that gracefully routes users without exposing internal endpoints.

Q29. How is logging configured and utilized across the application?
Answer:
We use SLF4J (Simple Logging Facade for Java) backed by Logback:

Declared via private static final Logger log = LoggerFactory.getLogger(ClassName.class);.
Uses parameterized logging (log.info("Registered HR '{}' for company '{}'", username, companyName);) to prevent unnecessary string concatenation overhead.
Log levels are configured in application.yml (org.springframework.security: INFO, com.hr.sphere: INFO).
Q30. Why did you set spring.jpa.open-in-view: false in application.yml?
Answer:
By default, Spring Boot keeps the database connection and Hibernate Session open throughout the entire HTTP request lifecycle (Open Session in View pattern).
Setting open-in-view: false ensures connections are released back to the HikariCP pool immediately after service/repository execution finishes, significantly reducing connection pool exhaustion and preventing accidental database queries inside UI rendering templates.

Q35. How would you handle transactional integrity when generating payroll or onboarding a company?
Answer:
By annotating service methods with @Transactional (org.springframework.transaction.annotation.Transactional).

🎯 Section 7: Testing, Problem Solving & HR Readiness (Q36 – Q40)
Q36. What was the most technically interesting problem you solved in this project?
Answer:
"The most interesting challenge was designing the Cascade Access Lock in a multi-tenant environment. Initially, one might think of running an expensive batch database update (UPDATE app_users SET status = 'INACTIVE' WHERE company_id = ?) whenever a company is suspended. However, that causes race conditions, heavy database I/O, and makes reactivating difficult because original user states are lost.
I solved this elegantly at the framework level by overriding UserDetails.isEnabled() in AppUser to evaluate both the user's status and their parent company's status in a single check during authentication. This resulted in an instant, zero-database-mutation organization-wide lockout."

Q37. How would you write unit and integration tests for this application?
Answer:

Unit Testing: Using JUnit 5 and Mockito (@ExtendWith(MockitoExtension.class)) to mock repositories and test controller/business logic in isolation.
Repository Testing: Using @DataJpaTest with an in-memory test database to test custom queries.
Web Layer Integration Testing: Using @WebMvcTest and MockMvc to test security filters, status codes, and model attributes.
End-to-End Integration Testing: Using @SpringBootTest(webEnvironment = WebEnvironment.RANDOM_PORT) with TestRestTemplate.
Q38. Why did you choose Server-Side Rendering with Thymeleaf instead of a separate React/Angular frontend?
Answer:

Rapid Delivery: Thymeleaf integrates seamlessly with Spring Security tags and Spring MVC models without requiring separate API boilerplate, CORS setup, and client routing.
Security by Default: HTML escaping is enabled by default to prevent Cross-Site Scripting (XSS).
Zero Client Build Overhead: Eliminates Node.js build pipelines and heavy JavaScript bundles, resulting in fast first-contentful paint (FCP) times.
Q39. If an employee reports they cannot log in, what systematic steps would you take to troubleshoot?
Answer:

Check Logs: Inspect Spring Security debug logs for authentication failures (UsernameNotFoundException or BadCredentialsException).
Check User Account Status: Query app_users table to confirm status = 'ACTIVE'.
Check Company Status (Cascade Lock): Verify if the user's company in companies is SUSPENDED.
Verify Password Encoder: Ensure credentials were encrypted using BCrypt rather than saved as plain text.
Check Database Connectivity: Verify that the persistent file database ./data/hrspheredb.mv.db is accessible.
